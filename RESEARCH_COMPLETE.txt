================================================================================
CRITICAL SUCCESS FACTORS
================================================================================

1. Use @Container static fields (not instance fields)
   Why: Ensures single container per test class, reused across methods

2. Use @DynamicPropertySource for runtime property injection
   Why: Containers get random ports, properties must be dynamic

3. Use @BeforeEach with TRUNCATE for per-test cleanup
   Why: 1000x faster than container recreation

4. Parallelize at class level (not method level)
   Why: Test classes are independent, methods share state

5. Use Awaitility for async assertions
   Why: Properly handles async Kafka consumer processing

6. Use Alpine images for 60% faster startup
   Why: Smaller container size, same functionality

7. Enable container reuse locally only
   Why: Speeds up development, CI/CD needs fresh containers

8. Use builder pattern for test data
   Why: Eliminates duplication, improves readability

ALTERNATIVES EVALUATED
================================================================================

Alternative 1: Embedded Kafka + H2 Database
├─ Advantages: Fast startup, no Docker
├─ Disadvantages: Not production-like, misses real issues
└─ Verdict: Good for unit tests only

Alternative 2: Docker Compose (Manual Setup)
├─ Advantages: Clear configuration
├─ Disadvantages: Manual setup, version management, CI/CD friction
└─ Verdict: Good for local dev only

Alternative 3: Per-Test Containers (New container each test)
├─ Advantages: Complete isolation
├─ Disadvantages: 8-12 seconds per test, slow (10+ minutes total)
└─ Verdict: Too slow for integration test suite

Alternative 4: Mocks/Stubs
├─ Advantages: Fastest execution
├─ Disadvantages: False test confidence, misses real bugs
└─ Verdict: Use only for unit tests

Recommended: TESTCONTAINERS (Shared static containers)
├─ Advantages: Production-representative, fast, parallelizable
└─ Verdict: BEST for integration testing
